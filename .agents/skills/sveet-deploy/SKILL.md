# Deploy a sveet app

`bun run deploy` = `bun run verify && fly deploy`. Fly builds the Dockerfile remotely. The image holds one executable (`build/server`, compiled by adapter-bun) plus `drizzle/`. The server applies pending migrations when it starts. SQLite lives on a Fly volume at `/data`.

**Deploys happen on the host, never in the sandbox.** If `SVEET_SANDBOX=1` is set, you are inside the VM: there is no flyctl or Fly token there, and `bun run deploy` refuses on purpose. Prepare everything you can (fly.toml, docs, `bun run verify`), then give the user the exact commands to run on their machine, one step at a time, and wait for them to report back.

Every `fly` command below changes a real account, so confirm each one with the user before running it. Show the command, say what it does, and run it once they agree. `fly auth whoami` tells you whether they're logged in.

## First launch

1. `fly.toml` ships with `app` and `ORIGIN` empty, so nothing deploys by accident. `sveet-setup` fills them in; if they are still empty, ask the user for the app name and URL and fill them in now.
2. Create the app: `fly apps create <app>`. If the name is taken, pick another and update `fly.toml` plus `ORIGIN`.
3. Create the volume: `fly volumes create data --size 1 --region <primary_region> --app <app>`. The name must match `[[mounts]] source`.
4. Set the secrets. Never commit them, never put them in `fly.toml`:
   ```sh
   fly secrets set BETTER_AUTH_SECRET="$(openssl rand -base64 32)" --stage
   fly secrets set SCW_SECRET_KEY=… SCW_DEFAULT_PROJECT_ID=… --stage   # Scaleway mail
   ```
   If mail isn't ready yet, set `MAIL_TRANSPORT = 'console'` in fly.toml for now. Sign-in links then only show in `fly logs`. Say so plainly: real users can't sign in until mail works.
5. `bun run deploy`. Then `fly logs` should show `Listening on …` and no env errors. Open `ORIGIN`, sign in, and confirm the mail arrives.

### Mail domain (Scaleway TEM)

In the Scaleway console, create a project, then add the domain `mail.<domain>` under Transactional Email (`fr-par`). Add the SPF, DKIM, DMARC and MX records it lists at the DNS host, and wait for "verified". Create an IAM application whose only permission is sending email in that project; its secret key is `SCW_SECRET_KEY`. `MAIL_FROM` must be an address on the verified domain. Point `MAIL_REPLY_TO` at a mailbox that is read, because `login@mail.…` can't receive mail.

### Custom domain

`fly certs add <domain>`, then add the DNS records it prints. Set `ORIGIN` in fly.toml to `https://<domain>` and redeploy. Better Auth builds sign-in links from `ORIGIN`.

## Routine

- **Ship**: `bun run deploy`. With one machine and SQLite, each deploy has a few seconds of downtime. Tell the user if they have live traffic.
- **Schema changes** ship automatically: commit the migration generated by `db:generate`, then deploy. Migrations must be additive and backwards-compatible; a failed migration stops the server from starting. Check `fly logs`.
- **Rollback**: `fly releases`, then `fly deploy --image <previous image ref>`. A rollback does not undo migrations.
- **Logs and status**: `fly logs`, `fly status`, `fly machine list`.

## Scaling and cost

- The default scales to zero (`auto_stop_machines = 'stop'`, `min_machines_running = 0`), which costs a few dollars a month. Once cold starts annoy users, set `auto_stop_machines = 'off'` and `min_machines_running = 1`.
- **Scale up, not out.** The volume mounts on one machine. A second machine would get an empty database. Use `fly scale vm` / `fly scale memory`. Running more than one machine means moving the database first (e.g. LiteFS or Turso). That's a project of its own, so tell the user that rather than bumping `count`.
- Grow the volume before it fills: `fly volumes extend <id> --size <GB>`.

## Production data

- Fly takes daily volume snapshots (`fly volumes snapshots list`). Before risky migrations, also copy the database off: `fly ssh sftp get /data/sqlite.db ./backup-$(date +%F).db`.
- `fly ssh console` opens a shell in the image (debian-slim, no bun). For SQL, copy the file down and use `sqlite3` locally, or add the `sveet-admin` skill's CLIs to the image.
- Never wipe production data without the user saying so explicitly.

## Not Fly

The image is plain Docker and runs anywhere: `docker build -t app . && docker run -p 3000:3000 -v app-data:/data -e ORIGIN=… -e BETTER_AUTH_SECRET=… app`. Behind a proxy, set `ADDRESS_HEADER` (and `XFF_DEPTH` for `x-forwarded-for`) so rate limits see real client IPs. Then replace `fly-client-ip` in `src/lib/server/auth-config.ts` with the same header.
